- 예외처리 정책
    
    ## 예외처리 정책
    
    ### 1. AI 애널리스트 주제 이탈 (정책 코드(제안): OFF_TOPIC · AI 호출 없이 고정 응답)
    
    사용자가 로또 번호 분석, 회차 분석, 통계, 발급번호 분석과 관련 없는 질문을 하면 답변하지 않고 안내한다.
    
    예시 응답:
    
    ```
    해당 질문은 로또 분석 주제에서 벗어난 질문입니다.
    AI 애널리스트는 로또 번호, 회차, 통계, 발급번호 분석만 도와드릴 수 있습니다.
    자세한 사용법은 오른쪽 상단 메뉴의 사용법 가이드를 참고해주세요.
    ```
    
    ### 2. 당첨 보장 요구 (정책 코드(제안): GUARANTEE_REQUEST · AI 호출 없이 고정 응답)
    
    사용자가 “당첨 번호 알려줘”, “1등 되는 번호 줘”, “확률 높은 번호 줘”처럼 확정 표현을 요구하면 보장하지 않는다고 안내한다.
    
    예시 응답:
    
    ```
    저희 서비스는 역대 로또 데이터를 분석해 참고용 번호 조합을 추천합니다.
    로또 추첨은 무작위로 이루어지므로 당첨을 보장할 수 없습니다.
    제공되는 조합은 통계 기반 참고 정보로만 이용해주세요.
    ```
    
    ### 3. 꿈풀이 관련성 부족 (정책 코드(제안): DREAM_LOW_RELEVANCE · AI 호출 없이 고정 응답)
    
    꿈 내용이 너무 짧거나 해석할 상징이 부족하면 안내 후 참고용 조합을 제안한다.
    
    예시 응답:
    
    ```
    입력하신 꿈은 로또 꿈풀이와 직접 연결할 상징이 많지 않습니다.
    그래도 일부 키워드와 통계 데이터를 바탕으로 재미로 참고할 수 있는 번호 조합을 만들어드릴 수 있습니다.
    ```
    
    ### 4. 구매 유도 요청 (정책 코드(제안): PURCHASE_PUSH · AI 호출 없이 고정 응답)
    
    사용자가 “이 번호 사면 돼?”, “무조건 구매할까?”처럼 구매 결정을 묻는 경우 직접 구매를 권하지 않는다.
    
    예시 응답:
    
    ```
    저희 서비스는 로또 구매를 권장하거나 강요하지 않습니다.
    제공되는 번호는 통계 기반 참고 조합이며, 최종 선택은 사용자 본인의 판단에 따라 결정해주세요.
    ```
    
    ### 5. 과몰입·절박한 요청 (정책 코드(제안): DESPERATE_REQUEST · AI 호출 없이 고정 응답)
    
    사용자가 경제적 어려움, 빚, 절박함을 이유로 당첨 번호를 요구하면 조심스럽게 제한한다.
    
    예시 응답:
    
    ```
    로또는 당첨을 보장할 수 없는 무작위 추첨입니다.
    경제적 문제 해결 수단으로 로또를 이용하는 것은 권장하지 않습니다.
    저희 서비스는 참고용 통계 정보만 제공할 수 있습니다.
    도박 문제로 힘드시다면 상담전화 1336으로 상담받으실 수 있습니다.
    ```
    
    ### 6. 번호 입력 오류 (서버 입력 검증 오류 응답)
    
    사용자가 1~45 범위를 벗어난 번호, 중복 번호, 6개 미만 또는 초과 번호를 입력하면 수정 요청을 한다.
    
    예시 응답:
    
    ```
    로또 번호는 1부터 45까지의 숫자 중 중복 없이 6개를 입력해야 합니다.
    번호를 다시 확인한 뒤 입력해주세요.
    ```
    
    ### 7. 발급코드 조회 실패 (서버 조회 오류 응답(404))
    
    없는 발급코드를 입력하거나 조회가 불가능한 경우 안내한다.
    
    예시 응답:
    
    ```
    입력하신 발급코드를 찾을 수 없습니다.
    발급코드를 다시 확인해주세요.
    발급 내역이 오래되었거나 삭제된 경우 조회가 어려울 수 있습니다.
    ```
    
    ### 8. AI 응답 실패 (AI 오류 응답(503 또는 재시도 안내))
    
    AI 응답이 지연되거나 실패하면 재시도를 안내한다.
    
    예시 응답:
    
    ```
    현재 AI 분석 응답을 불러오지 못했습니다.
    잠시 후 다시 시도해주세요.
    번호 생성과 기본 통계 분석은 계속 이용할 수 있습니다.
    ```
    
    ### 9. 외부 데이터 조회 실패 (외부 API 오류 응답)
    
    당첨번호, 판매점, 회차 데이터 조회에 실패하면 공식 기준 안내와 재시도를 제공한다.
    
    예시 응답:
    
    ```
    현재 당첨번호 데이터를 불러오지 못했습니다.
    잠시 후 다시 시도해주세요.
    최종 당첨 결과는 동행복권 공식 발표를 기준으로 확인해주세요.
    ```
    
    ### 10. 인증 사진 업로드 오류 (파일 검증 오류 응답(400))
    
    파일 형식, 용량, 누락 문제가 있으면 다시 업로드하도록 안내한다.
    
    예시 응답:
    
    ```jsx
    사진 업로드에 실패했습니다.
    이미지 파일 형식과 용량을 확인한 뒤 다시 업로드해주세요.
    로또 용지만 잘 보이도록 촬영한 사진을 권장합니다.
    ```
    

    ### 11. 조합 제공 횟수 제한으로 번호 교체 (확정 시)
    
    같은 대상 회차에서 같은 조합이 이미 3회 발급되어 일부 게임의 번호가 바뀐 경우 어느 게임이 바뀌었는지 알린다.
    
    예시 응답:
    
    ```
    일부 게임의 번호가 다른 조합으로 교체되었습니다.
    교체된 게임: {게임 번호}
    변경된 번호를 확인한 뒤 발급 결과를 확인해주세요.
    ```
    
    ### 12. AI 이용 한도 초과
    
    AI 일일 호출 상한 또는 월 비용 상한에 도달하면 AI 기능만 중지한다.
    
    예시 응답:
    
    ```
    현재 AI 기능 이용이 일시 중단되었습니다.
    번호 생성과 통계 조회는 계속 이용할 수 있습니다.
    ```
    
    ### 12-1. 사용자별 하루 무료 횟수 초과 (오류코드 AI-004, 429)

    서비스 전체 한도와 달리 이 사용자의 무료 횟수만 소진된 경우다. AI 기능만 막고 번호 생성·통계는 계속 이용할 수 있다.

    예시 응답:

    ```
    오늘 무료 AI 이용 횟수를 모두 사용했어요. 내일 다시 이용해 주세요.
    번호 생성과 통계 조회는 계속 이용할 수 있어요.
    ```

    ### 13. 요청 횟수 초과
    
    짧은 시간에 요청이 많으면 잠시 후 다시 시도하도록 안내한다.
    
    예시 응답:
    
    ```
    요청이 너무 많습니다. 잠시 후 다시 시도해주세요.
    ```

    ### 14. 위치 사용 꺼짐 상태에서 내 위치 질문 (정책 코드(제안): LOCATION_REQUIRED · AI 호출 없이 고정 응답)

    지도 AI에서 "내 위치 기준" 같은 질문을 했는데 위치 스위치가 꺼져 있으면 위치를 쓰지 않고 안내한다.

    예시 응답:

    ```
    내 위치 기준 질문은 위치 사용을 켜야 답할 수 있어요. 지도 위의 위치 스위치를 켜고 동의해 주세요. 위치는 저장되지 않아요.
    ```

포르투나볼 AI 기능 명세서

- 목적: 사용자 메뉴와 관리자 운영 기능의 화면·백엔드·프론트·데이터 계약을 하나의 기준으로 관리한다.

## 1. 공통 구현 기준

| 항목 | 최종 기준 |
| --- | --- |
| 번호 생성 | 서버의 통계 알고리즘이 담당한다. AI가 당첨번호를 직접 계산하지 않는다. |
| 번호 생성 흐름 | 통계 결과 조회 → 선택한 통계 패턴 기준 후보 조합 생성 → 홀짝·고저·합계·구간·빈도·미출현·연속수·끝수 검증 → 같은 대상 회차에서 이미 3회 찬 조합 제외, 쏠림 패턴(1~31 위주·연속·등차수열) 감점 → 후보 점수화 → 일부 랜덤성 적용 → 결과 반환. 포함·제외 번호는 번호 생성 화면에서 받지 않고 AI 애널리스트 요청에서만 반영한다. 후보가 부족하면 통계 필터와 쏠림 감점만 완화하고 포함·제외 번호는 완화하지 않는다. |
| 임시 결과 | 생성 결과는 Spring Cache에 30분(설정값) TTL로 보관하고 확정 토큰만 클라이언트에 전달한다. |
| 발급 저장 | 사용자가 발급을 확정했을 때만 `number_issue`와 `issue_number`를 하나의 트랜잭션으로 저장한다. |
| 재생성 | 기존 임시 결과를 폐기한다. 확정하지 않은 번호는 DB에 저장하지 않는다. |
| 중복 조합 제한 | 서비스 전체 기준으로 같은 `target_round_no`·`combo_key` 조합의 확정 발급은 최대 3회(설정값)로 제한한다. 발급을 확정한 건만 집계하고 임시 결과는 집계하지 않으며, 대상 회차가 달라지면 새로 센다. `combo_issue_count`에서 `issued_count < 3` 조건으로 원자적으로 증가시킨다. 확정 시점에 이미 찬 조합이 있으면 그 게임만 다시 생성해 교체하고 사용자에게 알린다. 이미 찬 조합은 생성 단계에서도 제외한다. 이 제한은 당첨 확률과 무관하다. |
| 번호 저장 규칙 | 번호 6개는 오름차순으로 저장하고 `combo_key`도 오름차순 기준으로 생성한다. |
| 대상 회차 | 사용자 대상 회차는 `RoundPolicy`로 계산한다. 토요일 20:00:00(Asia/Seoul)부터 다음 회차이며 모든 번호 생성 기능이 같은 로직을 쓴다. 클라이언트가 보낸 회차는 믿지 않고, 발급 확정 시 다시 계산해 비교한다. 공식 데이터 수집 스케줄러의 최신 회차 확인과 분리한다. |
| 실제 데이터 | 회차·당첨금·판매점 데이터는 공식 API 또는 공식 출처 기반으로 수집한다. |
| AI 역할 | 통계 결과 설명, 자연어 질문 분류, 꿈 상징 해석만 담당한다. 당첨 보장·1등 예측·확률 상승 표현은 금지한다. |
| 저장 개인정보 | 회원가입 없이 `guest_token`을 사용한다. AI 대화 원문과 꿈 원문 전체는 기본 저장하지 않는다. |
| 공통 고지 | 모든 화면의 맨 아래 "유의사항" 영역에 `통계 기반 생성 번호입니다. 참고만 하세요. 당첨을 보장하지 않습니다.` 한 줄을 한 번만 표시한다(12px 이상, 배경 대비 4.5:1 이상, 로또볼·카드마다 반복하지 않음). 서비스 안내 페이지에는 전체 문구를 둔다. |
| 통계 패턴 | 핫넘버(HOT_NUMBER), 겨울잠 번호(WINTER_SLEEP), 밸런스 믹스(BALANCE_MIX), 하이로우 믹스(HIGH_LOW_MIX), 센터 존(CENTER_ZONE), 올 구간 스프레드(ALL_SECTION_SPREAD) 6개를 최근 20회·50회·100회 세 기간 기준으로 계산해 `stat_pattern_card`에 저장한다(번호 생성 기준은 100회로 고정). 패턴 카드는 "최근 N회 중 M회 해당"으로 표시하고 과거 사실로만 표기한다. 통계 탭마다 "이 통계로 번호 생성"을 제공하며 번호는 서버 알고리즘이 만든다. |
| 회차 통계 상태 | 회차별 통계는 준비 중(PREPARING) → 결과 대기(WAITING) → 확정(CONFIRMED)으로 관리한다(`stat_round_snapshot`). 다음 회차용 준비 통계를 미리 만들어 번호 생성에 쓰고, 토요일 20:00(Asia/Seoul)에 전환한 뒤 당첨번호 수집을 확인하면 확정한다. 스케줄러는 중복 실행되어도 결과가 같아야 한다. 이용자 화면에는 준비 중·확정 두 가지로 표시한다. |
| 공유 | 공개 화면에 "공유하기" 버튼 하나를 제공한다. 누르면 기기의 공유 창(Web Share API)이 열려 사용자가 받는 곳을 직접 고른다. 공유 창을 쓸 수 없으면 링크를 자동 복사하고 안내한다. 발급코드와 개인 식별 정보는 공유 내용에 넣지 않는다. |
| 루키 명당 | 루키 명당은 최근 1년 안에 1등 1회 이상 또는 2등 5회 이상을 충족한 판매점이다(두 조건 중 하나만 충족하면 되고, 총 당첨 횟수와 개점 시기는 따지지 않는다). 기준일은 최신 확정 회차의 추첨일이며, 기간(1년)과 횟수(1·5)는 설정값이다. 3등은 판매점별 자료를 구할 수 없어 적용하지 않는다. 명당은 총 당첨 횟수가 많은 판매점이며 별도 기준 횟수 없이 1등 횟수 많은 순(같으면 2등 횟수 순)으로 정렬해 횟수와 함께 보여 준다. 한 판매점에 명당과 루키가 함께 표시될 수 있다. 판정에는 당첨 회차가 있는 `store_winning_history`를 쓴다. 판정 결과는 업로드 반영 시 계산해 캐시하고, "확률이 높다"는 식의 표현 없이 "최근 당첨 이력이 생긴 판매점"으로만 표시한다. |

## 4. 공통 비기능 요구사항

| 구분 | 요구사항 |
| --- | --- |
| 보안 | API 키·관리자 비밀번호·외부 서비스 키는 프론트·문서·Git에 평문으로 저장하지 않는다. |

| 장애 대응 | API·스케줄러·AI 실패를 각각 로그로 남기고 재시도 가능한 상태를 제공한다. |
| 반응형 | 모바일·데스크톱에서 번호, 차트, 표, 관리자 목록이 겹치지 않아야 한다. |
| 안전 문구 | 통계 조합은 참고용이며 당첨 확률이나 결과를 보장하지 않는다는 문구를 표시한다. |

## 5. 완료 기준

- 사용자 10개 메뉴의 화면, API, 백엔드 처리, 프론트 상태가 연결된다.
- 번호 생성 결과는 캐시에 임시 보관되고 발급 확정 전에는 DB에 저장되지 않는다.
- 확정 발급은 `number_issue`와 `issue_number`에 원자적으로 저장된다.
- 토요일 20:00:00 이후 요청은 다음 회차를 대상으로 하고, 이전 임시 결과는 확정할 수 없다.
- 같은 회차의 같은 조합은 서비스 전체에서 4번째 확정 시 해당 게임만 다른 번호로 교체되고 알림이 표시된다.
- 공식 회차·당첨금·판매점 데이터가 스케줄러와 관리자 재수집으로 갱신된다.
- 통계·AI·꿈풀이 결과가 최종 고지와 함께 제공된다.
- 당첨 검증은 공식 회차 기준으로 수행되고 중복 검증이 차단된다.
- 익명 인증은 사진 1개·댓글 1개 기준으로 검수된다.
- 관리자 작업, AI 사용량, API 오류, 스케줄러 결과가 추적된다.
- DB 설계서와 MySQL 스키마가 30개 테이블과 동일한 컬럼·관계를 가진다.

# 데이터 구성 방식

## 1. 실제 데이터

| 데이터 구분 | 테이블명 | 데이터 출처 | 적재 방식 | 비고 |
| --- | --- | --- | --- | --- |
| 회차별 당첨번호 | `draw_round` | 동행복권 공식 회차 API | 1회차부터 최신 회차까지 자동 수집 | 실제 데이터 |
| 등수별 당첨금 | `draw_prize` | 동행복권 공식 회차 API | 회차 데이터 수집 시 1~5등 함께 저장 | 실제 데이터 |
| 등수별 당첨자 수 | `draw_prize` | 동행복권 공식 회차 API | 회차 데이터 수집 시 1~5등 함께 저장 | 실제 데이터 |
| 판매점 목록 | `lotto_store` | 공공데이터포털 CSV | CSV 다운로드 후 관리자 업로드로 DB 적재. 연 1회 갱신 | 실제 데이터. 좌표는 주소 기반 지오코딩으로 채운다 [추가 2026-10-16] |
| 판매점 당첨 이력 | `store_winning_history` | 동행복권 1·2등 배출점 엑셀(당첨 회차 컬럼 필요, 확인 전) | 관리자 업로드(연 1회) 후 판매점과 이름+지역으로 연결 | 실제 데이터. 루키 명당 판정의 기준. 회차 자료가 없으면 비어 있고 루키 명당을 판정하지 못한다 [추가 2026-10-16] |

## 5. 정리 기준

| 구분 | 작성 기준 |
| --- | --- |
| 실제 데이터 | 외부 공식 데이터 또는 공공데이터를 기반으로 DB에 적재한다. |
| 계산 데이터 | 실제 회차 데이터를 기준으로 서버에서 계산해 저장하거나 캐시에 보관한다. |
| 시연용 데이터 | 관리자 화면과 예외 상황을 보여주기 위해 최소한으로 작성한다. |
| 금지 기준 | 실제 회차 데이터와 당첨번호는 임의 더미 데이터로 만들지 않는다. |

# DB 테이블 설계서

현재 최종 설계 테이블 수는 32개다(2026-10-15 설계 26개 + 2026-10-16 추가 4개: `stat_round_snapshot`, `stat_pattern_card`, `store_win_summary`, `store_data_upload` + 2026-10-22 추가 2개: `service_like_total`, `service_like_daily`). 변경 내역은 "32. 이번 수정 이력"에 정리했다.

## 1. 설계 기준

| 항목 | 기준 |
| --- | --- |
| 회차 데이터 | 추첨 완료된 공식 회차만 `draw_round`에 저장하고, 1~5등 당첨금·당첨자 수는 `draw_prize`에 분리 저장 |
| 미래 회차 발급 | `number_issue.target_round_no`에 숫자로 저장하고 FK로 묶지 않음 |
| 대상 회차 계산 | 토요일 20:00:00 KST부터 다음 회차. 서버 공통 로직에서만 계산 |
| 발급 저장 | 생성 즉시 저장하지 않고, 임시 확정 토큰으로 확정한 번호만 `number_issue`와 `issue_number`를 하나의 트랜잭션으로 저장 |
| 번호 저장 규칙 | 번호 6개는 항상 오름차순으로 저장 (`number_1` < ... < `number_6`) |
| 조합 제공 제한 | 서비스 전체 기준으로 `(대상 회차, combo_key)`당 최대 3회. `combo_issue_count`로 관리. 임시 결과는 세지 않고 발급 확정 때만 센다. 회차가 바뀌면 횟수가 새로 시작한다. |
| 당첨 검증 | 추첨 후 `draw_round`에 회차가 저장되면 검증 실행 |
| 중복 검증 방지 | `winning_verification.issue_number_id`에 UNIQUE 적용 |
| 꿈 데이터 | 대표 상징, 별칭, 상황별 해석, 추천 번호, 출처를 분리 저장 |
| 콘텐츠 관리 | 공지사항과 고정 안내 페이지를 분리 관리 |
| 파일 관리 | 인증 사진 파일 정보를 별도 테이블로 관리하고 비공개 경로에 저장 |
| 관리자 추적 | 관리자 작업 이력을 별도 로그로 저장 (변경 전후 값은 `action_detail`에 기록) |
| 실제 데이터 | 회차 데이터는 동행복권 공식 데이터 기반 |
| NULL 기준 | 설명에 "NULL 허용"이라고 적은 컬럼 외에는 모두 NOT NULL |
| 시간 기준 | 모든 DATETIME은 서버 `Asia/Seoul` 기준 |
| 기본 문자셋 | `utf8mb4` |
| ERD 분할 | 핵심 서비스 14개(회차·발급·검증·통계·판매점·익명 인증·파일)와 꿈·콘텐츠·운영·AI 16개로 나누어 관리 |
| 회차별 통계 상태 | [추가 2026-10-16] 회차별 통계는 `stat_round_snapshot`에 준비 중 → 결과 대기 → 확정 상태로 저장한다. 확정 후에도 준비 중이던 통계는 삭제하지 않고 보관한다. |
| 통계 패턴 생성 | [추가 2026-10-16] 통계 탭마다 패턴 카드(`stat_pattern_card`)를 만들고, 패턴 번호 생성은 서버 통계 알고리즘이 한다. AI는 설명만 한다. |
| 판매점 당첨 집계 | [추가 2026-10-16] 판매점별 합계(1등 자동·수동·반자동, 2등)를 `store_win_summary`에 표시용으로 저장한다. 회차별 이력은 `store_winning_history`에 저장하고 루키 명당 판정에 쓴다. |
| 판매점 데이터 갱신 | [추가 2026-10-16] 공공데이터 파일과 동행복권 엑셀을 관리자가 연 1회 업로드한다. 반영 전에 기존 데이터와 비교하고, 새로 생기거나 바뀐 판매점만 지오코딩한다. 이력은 `store_data_upload`에 남긴다. |

| 항목 | 기준 |
| --- | --- |
| AI 예외처리 | 저비용 판단 AI가 입력을 분류하고 Spring Boot가 정책 실행 |
| 예외처리 정책 | DB에서 정책 코드·처리 방식·우선순위·안내 문구 관리 |
| 핵심 키워드 | 정책별 키워드를 별도 테이블에서 관리 |
| 문맥 판단 | 키워드 일치만으로 차단하지 않고 AI가 문맥 검토 |
| 일반 시스템 예외 | Spring Boot 코드와 기존 오류 로그 활용 |
| AI 응답 길이 | 챗봇 기본 답변 최대 500자 |
| 모델 교체 | 특정 AI 모델에 종속되지 않도록 정책 코드 표준화 |
| AI 대화 저장 | 대화 원문은 저장하지 않고 사용량·실패·처리된 정책 코드만 기록 |

| 테이블명 | 컬럼명 | 타입 | PK/FK | 설명 |

| `ai_usage_log` | `feature_type` | VARCHAR(30) |  | AI 기능 구분 |
| `ai_usage_log` | `request_status` | VARCHAR(20) |  | 성공/실패/차단 상태 |
| `ai_usage_log` | `model_name` | VARCHAR(50) |  | 사용 모델명 (AI 호출이 없었던 경우 NULL 허용) |
| `ai_usage_log` | `policy_code` | VARCHAR(50) |  | 적용된 예외처리 정책 코드 (NULL 허용) |
| `ai_usage_log` | `input_token_count` | INT |  | 입력 토큰 수 |
| `ai_usage_log` | `output_token_count` | INT |  | 출력 토큰 수 |
| `ai_usage_log` | `response_time_ms` | INT |  | 응답 시간(ms) (NULL 허용) |
| `ai_usage_log` | `estimated_cost` | DECIMAL(10,6) |  | 비용 추정값 (NULL 허용) |
| `ai_usage_log` | `error_message` | TEXT |  | 실패 사유 (NULL 허용) |
| `ai_usage_log` | `created_at` | DATETIME |  | 생성일자 |

- `model_name`, `policy_code`, `response_time_ms`, `estimated_cost`는 요구사항(BE-27, AD-09)을 충족하기 위해 추가했다.
- 채팅 원문과 꿈 원문은 저장하지 않는다.
- `estimated_cost`의 단위는 USD다. 월 비용 한도 판단에 `created_at` 기준 이번 달 합계를 쓴다.
- `request_status = BLOCKED`는 한도 초과·AI 키 없음으로 막힌 시도이며 `policy_code`에 `AI_NOT_CONFIGURED`, `AI_DAILY_LIMIT`, `AI_MONTHLY_COST_LIMIT`, `AI_USER_LIMIT`를 저장한다. 호출·비용으로 세지 않는다(`model_name`이 있는 행만 호출로 집계).
- 사용자별 하루 무료 횟수는 DB가 아니라 서버 메모리에서 센다(서버를 다시 시작하면 초기화). 사용자 식별값은 `ai_usage_log`에 저장하지 않는다. 유료 이용권을 붙일 때 잔여 횟수와 차감·환불 이력은 별도 테이블로 설계한다.

## 33. 구현 시 주의사항 [추가 2026-10-16]

- `number_issue.target_round_no`, `stat_round_snapshot.target_round_no`, `combo_issue_count.target_round_no`는 FK가 아니라 일반 INT이다.
- `store_win_summary.lotto_store_id`는 FK이면서 UNIQUE이다.
- `stat_round_snapshot.target_round_no`는 UNIQUE이며, 같은 회차의 통계가 2개 만들어지면 안 된다.
- `stat_pattern_card`는 `snapshot_id + pattern_code + period_rounds`가 UNIQUE이다. 번호 생성에는 `period_rounds = 100` 카드의 조건값만 쓴다.
- 회차별 통계 작업은 여러 번 실행해도 결과가 같아야 한다. 실패하면 이전 통계를 유지하고 `scheduler_log`와 관리자 알림을 남긴다.
- 패턴 번호는 서버 통계 알고리즘이 만들며, 같은 회차의 같은 조합은 서비스 전체에서 최대 3회까지만 허용한다. (`combo_issue_count`)
- 판매점 파일은 반영 전에 기존 데이터와 비교하고, 새로 생기거나 바뀐 판매점만 지오코딩한다.
- 내 위치와 검색 위치는 저장하거나 로그에 남기지 않고 AI에도 보내지 않는다.
- `lotto_store.sido`, `sigungu`, `store_type`, `api_error_log.request_url`은 NULL 허용으로 둔다. 원본 파일에 값이 없는 행이 있어도 적재나 로그 기록이 실패하지 않게 하기 위한 것이며, 확정 전이다.
- `ai_usage_log`의 토큰 수는 AI 호출이 없으면 0으로 저장한다.

확정이 필요한 항목:

- 동행복권 1·2등 엑셀에 당첨 회차 컬럼이 있는지(확인 전)
